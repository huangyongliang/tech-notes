# 来源与追溯 {#provenance}

> [DevOps](../) › 来源与追溯

来源证据回答一件制品是谁、用哪些材料、从哪一次源修订、由谁做出来的。它是可核对的陈述，不是安全结论。

## 这一页补哪一块 {#provenance-scope}

[Git 版本控制](../../cs-basics/04-git/) 写提交、分支和 PR 怎么用。本页只取「修订身份」这一层，不重讲命令。[持续交付与 GitOps](../../microservices/14-cicd-gitops/) 已把不可变标签和「期望状态放进 Git」写成实践。本页说明：没有稳定的制品身份，后面的晋级、回滚和审计都失去对象。不写 SBOM 格式教程，也不做签名工具对照表。

## 来源要回答的那几个问题 {#provenance-questions}

一份来源证据要能回答固定的一组问题：哪一次源修订，哪份构建定义，哪些输入，由哪个构建者，在什么时候，产出了哪一个制品身份。身份是摘要，不是一个以后还会改指向的标签。

少一项，后面的人就无法把「当时承认的那一份」和「现在这个名字指向的那一份」对上。SLSA 用 provenance 这类证明来承载这种陈述，并说明如何验证它。本页只用这组词汇。它不是一份逐级要勾选的合规清单。

v1.2 相对 v1.1 增加了 Source Track。源修订本身也可以有保证等级，例如历史是否被保留、这次修订是怎么产生的。这里只点明有这一档，不展开各级条款。2026-11-10 核对 [官方说明](https://slsa.dev/spec/v1.2/)，现行批准版仍是 v1.2，状态为 Approved。

## 提交号不是完整的构建来源 {#provenance-git}

Git 提交号是源修订的名字。它指出那一次快照的内容身份。它不自动包含工具链、依赖锁定和构建环境，也不自动阻止以后有人把分支名改指向另一次提交。

所以「仓库里看得到这个哈希」只完成了来源问题里的第一问。构建定义、输入和构建者仍要另有陈述。命令和分支怎么用，仍以 [Git 版本控制](../../cs-basics/04-git/) 为准。

## 身份钉在摘要上 {#provenance-digest}

制品身份用不可变摘要，不用 `latest` 这类会改指向的名字。两个时刻可以共用同一个标签，摘要却不同。标签回答不了「哪一份被承认过」。

没有稳定身份时，晋级无法说明搬过去的是验过的那一件，回滚无法指回旧的那一件，审计也无法在事后复述当时放行的是谁。镜像作为这种制品的一种形态，见 [容器与编排](../../microservices/12-containers-k8s/)，本页不讲构建指令。

短例子：标签 `app:release` 在周一指向摘要 D1，在周二指向摘要 D2。界面上两次都能「看到一个 SHA」，但看到的不是同一件制品。只有绑在 D1 上的来源陈述，才能判断 D1 被承认过；D2 要有自己的陈述。共用的标签证明不了这件事。

## 证明是陈述，不是结论 {#provenance-statement}

构建来源证明和材料清单（SBOM 一类）都是关于制品的陈述。陈述可以核对：它声称的修订、材料和构建者，是否和签名、摘要对得上。核对通过，只说明这份陈述没有被换成另一份，以及它说的是这一个摘要。

它不能单独推出「软件是安全的」或「软件是正确的」。材料清单列出用了哪些组件。列出来，不等于这些组件没有漏洞，也不等于程序做对了要做的事。SPDX 和 CycloneDX 都是在描述这种清单，本页不选哪一种格式。

签名把「身份」和「陈述」绑在一起。签的是摘要，验的是谁被信任。信任的是签发这张陈述的那一方，不是「因此有人审过代码」。签过名仍可能只是构建者在声明自己做了这次构建。把签名当成批准，是换了一个问题。

## 部署来源不能顶替构建来源 {#provenance-gitops}

部署侧和构建侧要分开。GitOps 把期望状态放进 Git，集群持续收敛到那份声明。它回答的是「集群在按谁声明的状态运行」。OpenGitOps 把这件事定义为原则；实践见 [持续交付与 GitOps](../../microservices/14-cicd-gitops/)，本页不重抄工具对照。

这份部署来源不能顶替「这个镜像是从哪次构建来的」。期望状态里即使写了一个镜像名，只要那个名字还能改指向，构建来源的问题就还在。两边都要有，而且指的不是同一层。

## 常见误读 {#provenance-misreadings}

- 「有 commit 哈希，来源就齐了。」提交号只命名源修订。工具链、依赖和构建者不在这个哈希里。
- 「有 SBOM 就说明软件安全。」清单是一份可核对的材料陈述，不是漏洞或正确性的结论。
- 「界面上能看到 SHA，所以用 `latest` 也没关系。」标签会改指向。周一的 SHA 和周二的 SHA 可以不同，而名字没变。
- 「签过名就是正确的、被批准的。」签名核验的是谁被信任、签的是哪个摘要。它不自动等于有人审过代码。

## 可选核对 {#provenance-check}

问题已经列在上面。这两问只核对哪一层证据还缺。

1. 一件制品带有 Git 提交号和一份材料清单。来源问题是否已经答完？
2. 两个镜像先后都叫 `app:release`，摘要不同。能不能用这个标签判断哪一份被承认过？

<details markdown><summary>参考答案</summary>

1. 还没有。提交号是源修订，材料清单是组件陈述。构建定义、构建者和制品摘要之间的绑定还要单独写明，并说明谁被信任来签发这张陈述。
2. 不能。标签是会改指向的名字。只有绑在某一个摘要上的来源陈述，才能判断那一份被承认过。
