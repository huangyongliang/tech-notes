# 晋级与门禁 {#promotion-gating}

> [DevOps](../) › 晋级与门禁

晋级把一件已被承认的制品和它的证据送进下一个环境。门禁只保证它实际检查过的那条命题。

## 环境是信任的台阶 {#promotion-steps}

环境是信任的台阶，不是目录标签。从预发到生产，晋级移动的是同一件制品及其证据，而不是「用同一提交在新环境里再做一次」。

这和 [可重复性](../01-repeatability/) 是同一份合同的下一句。那里保证输入没变时身份不悄悄改变。这里保证往前走的就是那一个身份，而不是一个新编出来的近亲。来源陈述如何绑到这个身份上，见 [来源与追溯](../02-provenance/)。

## 门禁只覆盖它检查过的命题 {#promotion-gates}

门禁是进入下一台阶所需的证据。它可以是自动检查、人工审批，或一条安全、变更策略。每一种只保证它实际检查过的命题。

流水线变绿，只等于所列检查当时通过。它不等于系统在生产里正确，也不等于没有跑到的路径是安全的。没写进门禁的命题，这次放行没有覆盖。

人工审批首先是责任门禁：它记录谁在何时放行。除非同时写清审批人必须看哪一份证据，否则它不自动变成技术保证。点了批准，可能只说明有人在场，不说明摘要被核对过、测试被看过。

## 测试结果是一种证据 {#promotion-tests}

测试结果是常见的一种证据。单元测试、契约测试各自能挡住的失败不一样。分层和契约怎么写，见 [微服务 15](../../microservices/15-testing/) 和 [Java 08](../../java/08-testing/)，本页不重复。

适合挡在哪一级，取决于那一级要相信什么。还没离开构建的台阶，适合挡住「这件制品连自己的单元约定都不满足」。进入预发之前，适合挡住「它和上下游的契约对不上」。这些检查没跑到的路径，不会因为流水线是绿的就被覆盖。门禁的边界就是测试实际执行过的那一组命题。

## 流量晋级不是制品晋级 {#promotion-traffic}

渐进交付把流量也当作晋级对象。金丝雀或蓝绿先把一小部分流量交给这件制品，再扩大。它保证的是：风险先暴露在限定范围内，而不是一开始就面对全部用户。

它不替代制品晋级。顺序是先有同一份制品，再切流量。没有「验过的就是要上的」这一条，切流量只是在切一份还没被承认的新构建。步骤和自动回滚条件的写法见 [微服务 14](../../microservices/14-cicd-gitops/)。切流时可以看的信号见 [可观测性](../../microservices/10-observability/)，本页不讲采集栈。

## 搬过去，还是再编一次 {#promotion-contrast}

对照两条路。预发验过制品 A：

1. 晋级：生产运行 A，来源证据跟着 A 走。验过的就是要上的。门禁若要求摘要一致，换一件就会被拒绝。
2. 重建：生产用同一提交再编译出 A′。即使提交号相同，A′ 也是另一件制品，除非摘要被证明相同。预发的验证不再自动覆盖生产正在跑的那一份。

第二条撤回的就是本章要守的约定。它不是「针对该环境做了更严格的验证」。环境差异要另写检查；用重新构建来冒充那项检查，两件事都没做成。

## 常见误读 {#promotion-misreadings}

- 「流水线全绿，生产就不会出事。」绿只等于所列检查当时通过。没写进门禁的命题，这次放行没有覆盖。
- 「每个环境重新构建，才叫针对该环境做了验证。」重新构建撤回的是「验过的就是要上的」。环境差异要另作检查，不能靠再编译来冒充。
- 「有人点了批准，就等于做过技术检查。」审批记录的是谁在何时放行。只有写明必须看的证据，它才同时是技术门禁。
- 「金丝雀是发布工具的功能，和晋级策略无关。」它是把流量当作晋级对象：先在限定范围内暴露风险。它仍然要求先有同一份制品。

## 可选核对 {#promotion-check}

台阶和门禁已经分开写了。这两问只核对放行覆盖了哪一条。

1. 所有自动检查都绿了，又有人点了批准，但审批说明里没有要求核对制品摘要。这次放行保证了摘要没被换成另一件吗？
2. 生产用同一提交重新构建，再把 5% 的流量切过去。这是制品晋级吗？

<details markdown><summary>参考答案</summary>

1. 不保证。自动检查只覆盖它们实际跑过的命题。没写明「必须核对摘要」的批准，记录的是有人放行，不是摘要身份。
2. 不是。重新构建得到的是另一件制品，除非摘要被证明相同。切 5% 流量是流量晋级，它不能把一次新构建说成预发验过的那一份。

</details>
