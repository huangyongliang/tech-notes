# 恢复能挽回什么 {#what-recovery-can-restore}

> [SRE 与高可用](../) › 恢复能挽回什么

恢复作用在还没花完的误差预算上。它阻止继续失败。已经失败的请求不会因此变成成功。

## 这一页补哪一块 {#recovery-scope}

[服务水平与误差预算](../02-slo-error-budget/) 写失败份额如何被花掉。本页写发现、缓解和修复怎样作用在这份份额上。撤回制品的条件在 [回滚与审计](../../devops/04-rollback-audit/)。数据已经按新规则写过、超时不等于没做，分别见 [分布式事务](../../microservices/07-distributed-transactions/) 和 [分布式系统模型](../../systems/distributed/)。本页不写值班日历，不写事后复盘模板，也不写具体的恢复命令。

## 三段时间 {#recovery-time}

把一次受损拆成三段，不必先记一串缩写。

发现：从用户已经按第 01 章的定义受损，到有人按这个定义看出受损。开始缓解：从看出，到失败份额停止继续增加。完全修复：从缓解稳住，到原因去掉、服务水平回到目标之内。

缩短发现和开始缓解，通常比在同一窗口里把平均无故障时间拉得更长，更能保护时间占比或请求占比。无故障时间更长，说的是两次受损之间更久。窗口里一旦已经在失败，拖着不缓解，失败份额会继续按时间或按请求累加。更快止住，花掉的预算更少。平均无故障时间再长，也换不回已经花掉的那一段。

## 挽回的是后继，不是已失败的请求 {#recovery-object}

恢复的对象是服务水平，不是「机器又起来了」。与第 01 章对齐：用户请求已经失败的那一部分，预算已经被花掉。恢复阻止的是继续花费，不是把已失败的请求改写成成功。进程重新起来，若用户的那一类操作仍在失败，服务水平就还没恢复。机器状态和定义里的成功不是同一个对象。

## 撤回制品只在它造成失败时有用 {#recovery-rollback}

回滚回到先前承认的制品。条件在 [回滚与审计](../../devops/04-rollback-audit/)：旧制品还在，身份还在，并且当前数据仍是旧制品能工作的那种。当失败由这次晋级引起，而且旧制品仍能在当前数据下工作，回滚可以是快的缓解：失败率停下，预算停止继续被花。

若失败来自依赖，或数据已经按新规则写过，或规格从未被满足，撤回制品挽回不了可用性。依赖还在失败，回到旧制品仍然失败。数据已经向前，旧制品可能按自己的约定拒绝或读错，这是 DevOps 那一章已经分开的限制。规格从未写清或从未被实现满足，撤回只是换一份仍不满足的实现。部分失效下，超时仍说明不了那次请求做成没有。本页不重写这些模型，只把它们映射到预算：挽回不了的失败，预算里已经记上，而且不会被回滚涂掉。

## 先挡住，再找原因 {#recovery-mitigate}

缓解可以低于完整修复。先关掉有问题的路径、减小影响范围，让失败份额停止增加。然后再找原因。缓解必须仍满足第 03 章的条件：不能靠「再重启一次所有副本」冒充失败独立。一起重启共享同一原因的副本，只是把共同命运再演一次。

一次错误发布已经在窗口里花掉部分预算。快速回滚若满足上一节的条件，失败率停下，同一窗口里 SLO 只承担已经花掉的份额，余下请求不再按错误发布的失败率继续花。长时间排查却不缓解，失败率一直维持，窗口结束时花掉的份额更大，SLO 更容易被打破。排查没有错。它不代替缓解。这不是复盘模板，只是同一窗口里两种花费。

## 常见误读 {#recovery-misreadings}

- 「恢复了就等于这些失败没发生过。」已经失败的请求花过的预算还在。恢复止住的是后面的花费。
- 「回滚一定能挽回可用性。」只有失败来自这次晋级，且旧制品仍能在当前数据下工作，回滚才是快的缓解。依赖、已前进的数据和从未满足的规格，撤回制品都补不上。
- 「平均无故障时间更长，一定比更快缓解更重要。」无故障时间不把已经在发生的失败份额买回来。同一窗口里，更快止住花得更少。
- 「有值班和手册，恢复理论就不需要了。」手册可以写步骤。它不定义服务水平，也不把已失败的请求改成成功。

## 可选核对 {#recovery-check}

花费和撤回已经分开。这两问只核对挽回了什么。

1. 回滚之后失败率停止上升。窗口里已经失败的那些请求，还算花掉预算吗？
2. 数据已经按新规则写过，旧制品一接上就拒绝这些数据。这次回滚挽回可用性了吗？
