# 请求处理与中间件 {#request-handling}

> [Web](../) › 请求处理与中间件

后端框架约定的是：一次已经到达应用的请求，如何按映射和顺序变成响应。映射本身不是 HTTP，跑通也不等于业务正确。

## 这一页补哪一块 {#request-scope}

[计算机网络](../../cs-basics/05-networking/) 写报文和状态码。本页不重讲那一章。状态码的含义仍以 HTTP 为准，不随某个框架的路由表改变。[Spring](../../java/09-spring/) 写 MVC 和 WebFlux 怎么实现。本页不写注解清单，也不教数据库访问。

[API 网关](../../microservices/02-api-gateway/) 是多服务前面的入口。[服务通信](../../microservices/04-communication/) 是服务之间的客户端。两者都不是「一个应用进程里，请求从进来到出去」的那条管道。

## 映射只说明谁被调用 {#request-route}

资源在这里是应用承认的一对：哪个 URL、哪种方法，交给哪一段逻辑。框架保证的是这张映射，以及它调用这段逻辑的时机。它不保证订单真的该被创建，也不保证金额算对了。

路由表是应用的约定，不是 HTTP 的一部分。协议规定请求行长什么样、状态码表示什么。框架规定「这条请求行进来之后，调用哪一个处理函数」。没有这张表，HTTP 仍然是 HTTP；有了这张表，也不表示协议多了一条方法。

## 链的顺序是约定的一部分 {#request-chain}

中间件或过滤器是插在「进来」和「出去」之间的步骤：解析体、鉴权、记日志、把错误收成统一的响应。经典的过滤器模型是一条链：每一环决定把请求继续交下去，还是就地结束。容器或框架按声明的顺序调用它们。这个顺序是模型的一部分，不是某个框架版本的私货。本页不绑定某一版 Servlet 或 Spring。

顺序敏感，因为每一环看见的请求不一样。

- 先解析再鉴权：未通过身份的请求也会把体读进来。解析本身可能很贵，也可能在鉴权之前就按体里的内容做了动作。
- 先鉴权再碰体：没通过的请求不会进入解析和处理。鉴权看不见体里的字段，除非它自己再读一次。

两种都可以是合法约定。不能从「能跑通」推出顺序无所谓。调换之后，被保护的命题就换了。

## 网关不是这条链的同义词 {#request-gateway}

反向代理和 API 网关站在多个服务前面，做入口路由、鉴权和限流。那是另一条边界，见 [API 网关](../../microservices/02-api-gateway/)。本页只讨论单个应用进程内的管道。

有网关，应用里的管道还在。网关放行之后，请求仍要在应用里被映射、被链上的步骤处理。把网关过滤器写成应用中间件的同义词，会让人以为入口策略已经代替了应用自己的鉴权和解析。服务间的客户端调用也不是这条管道，见 [服务通信](../../microservices/04-communication/)。

## 异步没有取消超时 {#request-async}

同步处理时，一个线程从进入处理函数等到响应写完。异步或非阻塞模型改的是谁在何时占用线程：等待外部结果时可以先让出线程。它不改「这一次请求有没有在截止时间前得到响应」。

超时仍然是这条管道上的事实。客户端或代理可以先放弃，应用稍后才写完。非阻塞只改变等待时占不占着线程，不保证响应一定来得及。实现上 MVC 和 WebFlux 的差别见 [Spring](../../java/09-spring/)，本页不把其中一种写成 Web 平台的默认。

## 一次 POST 的四步 {#request-derivation}

约定写成「解析 → 鉴权 → 处理 → 写响应」时，一次 `POST /orders` 是：

1. 解析：体被读成订单草稿。还没有创建订单。
2. 鉴权：确认调用者可以创建订单。没通过就停止，草稿不进入处理。
3. 处理：按草稿创建订单。业务对不对，是这一步的事，不是路由表的事。
4. 写响应：把处理结果变成状态码和正文。状态码的含义仍按 HTTP，不按框架的函数名。

抽掉鉴权：未确认身份的请求也会创建订单。被破坏的是「只有通过身份的调用者才能进入处理」。

把写响应提前到处理之前：客户端收到的是还没创建订单的结果。被破坏的是「响应描述的是处理之后的状态」。

两条都可能仍然返回 200。200 只说明 HTTP 语义里的成功，不说明上面那份应用约定还在。

## 常见误读 {#request-misreadings}

- 「框架路由就是 HTTP 协议的一部分。」路由是应用把请求行映射到处理函数。协议不因为多了一张路由表而改变。
- 「有网关了，应用里就不用谈请求管道。」网关是多服务入口。请求进入某一个应用之后，映射和中间步骤仍是那个进程里的约定。
- 「中间件顺序无所谓，能跑通就行。」先解析还是先鉴权，决定未授权的请求会不会碰体、会不会进入处理。
- 「用了 WebFlux 或异步，超时就不会发生。」异步改变的是等待时占不占线程。截止时间仍然可以先到。

## 可选核对 {#request-check}

管道和协议已经分开。这两问只核对约定还在不在。

1. 应用把 `POST /orders` 映射到一个函数，并返回 201。这是否说明 HTTP 新增了一种「创建订单」方法？
2. 链从「鉴权 → 解析 → 处理」改成「解析 → 处理」，鉴权被拿掉，测试仍返回 200。约定有没有变？

<details markdown><summary>参考答案</summary>

1. 没有。201 仍是 HTTP 的状态码。映射只说明这个应用用哪个函数处理这对 URL 和方法。
2. 变了。未通过身份的请求现在也会进入处理。能返回 200 只说明响应写出去了，不说明「先鉴权」还在。

</details>
