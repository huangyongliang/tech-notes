# 浏览器里的源 Browser Origin

浏览器把文档和脚本按源隔开。源由方案、主机和端口组成，不是「看起来像同一个网站」。

## 这一页补哪一块

[计算机网络](../../cs-basics/05-networking/) 已经写了 HTTP 的请求行、状态码，以及 TLS 保护传输、并用证书核对域名。那一章没有写：页面里的脚本能不能读到另一个地址的文档或响应正文。本页只写浏览器的这个边界。它不教 HTML 标签，也不教后端框架。

## 源是三元组

HTML 现行标准把源当作 Web 平台的权限单位。一个元组源包含方案、主机和端口。两个元组源相同，当且仅当方案相同、主机相同、端口相同。路径不参与比较。

以 `https://shop.example/cart` 为基准，默认端口是 443：

| URL | 是否同源 | 原因 |
|-----|----------|------|
| `https://shop.example/api/orders` | 是 | 只多了路径 |
| `http://shop.example/cart` | 否 | 方案从 https 变成 http |
| `https://shop.example:8443/cart` | 否 | 端口不是 443 |
| `https://api.shop.example/cart` | 否 | 主机不同 |

这张表是在套定义，不是在某一种浏览器里点出来的实验结果。`file:` 的源由实现决定，标准并不保证同一目录下的两个本地文件同源。本页的结论限于有方案、主机和端口的网络源。

## 同源策略限制什么

同源策略限制一个源里的文档或脚本如何接触另一个源的资源。MDN 把典型风险写成：恶意页面里的脚本不应读到用户已登录的第三方邮箱，或只在内网才能打开的页面。

脚本直接拿另一个窗口的文档时，不同源只能做很窄的一组操作，例如 `postMessage`。读对方的 DOM、或把 `fetch` 的响应正文交给脚本，默认不行。存储也按源分开：一个源的脚本不能读写另一个源的 Web Storage 或 IndexedDB。

跨源的写和嵌入常常被允许。链接、表单提交属于写。用 `img` 或 `script` 嵌进页面，会漏出一些信息，例如图片尺寸或脚本有没有加载成功，但不是把响应正文交给你的脚本。所以「请求发出去了」不等于「脚本读到了正文」。

## 和 TLS、Cookie 不是同一层

证书证明传输对端持有该域名的私钥。[计算机网络](../../cs-basics/05-networking/) 写过：合法证书不证明网站内容可信。它同样不证明另一个源的脚本可以读你的页面。`https://evil.example` 可以有自己的合法证书，它和 `https://shop.example` 仍然不同源。

Cookie 用另一套范围。页面可以为自己的域或父域设置 Cookie，父域不能是公共后缀；读取时看不出这条 Cookie 当初是从哪个源写下的。因此「带上 Cookie」不是「两个 URL 同源」。HTTP 无状态说的是协议本身不记住上一次请求，登录状态要靠 Cookie 或令牌再带上。无状态并不取消浏览器对脚本的源隔离。

## CORS 是服务器的放行，不是把边界删掉

跨源读取默认不交给脚本。CORS 是 HTTP 的一组响应头，用来声明浏览器可以把这次跨源响应暴露给哪个源的脚本。服务器没有给出允许时，浏览器可以已经发出了请求，但仍不把正文交给脚本。把 CORS 说成「关闭同源策略」会漏掉这一步：放行的是某一次读取，边界还在。

## 常见误读

- 「路径不同就不同源」。`/cart` 和 `/api/orders` 在方案、主机、端口相同时同源。
- 「用了 HTTPS 就可以互相读页面」。TLS 保护传输并核对域名，不合并源。
- 「请求返回 200，脚本就拿到了 JSON」。跨源时，状态码属于响应；脚本能否读取正文还要看同源或 CORS。
- 「Cookie 的域和源是同一个三元组」。Cookie 的域可以是父域，而且读的时候不显示写入时的源。
