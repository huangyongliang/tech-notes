# 验证能证明什么 {#verification}

> [软件工程理论](../) › 验证能证明什么

验证是拿一种手段对照规格，或对照规格的一部分。手段不同，能建立的结论不同。通过一次检查，只覆盖这次手段实际碰到的范围。

## 这一页补哪一块 {#verification-scope}

第 03 章写规格是可检查的性质约定。本页写检查手段的效力边界。不写测试框架，不写流水线配置，也不重讲测试金字塔。[Java 08](../../java/08-testing/) 和 [微服务 15](../../microservices/15-testing/) 是分层在具体栈上的写法。本页只说明分层改变范围和代价，不改变「没跑到的行为没有被这次测试证明」。

## 没有规格，通过只是没失败 {#verification-needs-spec}

验证要把一种手段对照到规格，或规格里写明的那一部分。没有规格，检查通过只说明这次跑过的步骤没有失败。它不能说明软件满足了应有的性质，因为「应有」还没写成可检查的约定。预言本身也必须正确：期望值写错了，测试通过说明的是「得到了那个错误的期望」，不是性质成立。

## 测试显示缺陷在，不显示缺陷不在 {#verification-testing}

Dijkstra 在 EWD268 里写过：程序测试可以用来显示缺陷的存在，但绝不能显示缺陷的不存在。理由是输入的组合多到不能靠抽样穷尽。因此他主张正确性的论证应依赖程序文本，而不是依赖把所有计算都跑一遍。同一份笔记也写明，当时能给出的证明例子很小，证明的工作量可能随程序变大而爆炸。所以形式推理不是「能证明一切」，也不是「工程里完全不能用」。

测试的成立条件就这两条：只覆盖被执行的输入和路径；预言必须是规格里那条性质的正确读法。覆盖率量的是跑过了多少结构，不是正确性。百分比升高，只说明更多结构被执行过。没执行的路径、没写进预言的性质，仍然没有被这次测试证明。

## 手段并列，不排座次 {#verification-means}

下面不是价值排序。每一行只写该手段在其条件下能建立什么。

| 手段 | 能建立的 | 不能建立的 |
|------|----------|------------|
| 测试 | 被执行的输入上，预言失败或没有失败 | 未执行路径无缺陷；预言错了则结论跟着错 |
| 类型检查 | 拒绝语言规则禁止的一类程序 | 规格里类型不管的那些性质 |
| 代码审查 | 发现约定没被执行，或规格写得含混 | 代替执行；没被读到的路径 |
| 流水线门禁 | 当时列入的检查已经通过 | 没列入的性质 |
| 形式推理 | 规格写清且假设成立时，特定性质被证明 | 一切性质；假设不成立时的结论 |

类型检查的效力以 [编程 03 类型系统](../../programming/03-types/) 为准：通过检查不等于程序正确，它拒绝的是类型规则写明要拒绝的程序。门禁的效力以 [晋级与门禁](../../devops/03-promotion-gating/) 为准：全绿只等于所列检查当时通过。形式推理的位置在 [理论基础](../../cs-theory/)，本页不教证明器。审查能读到规格和代码是否对得上，但不能代替那些没被执行的计算。

分层（单元、契约、端到端）改变的是检查的范围和代价。单元没碰到的协作，端到端没碰到的输入，都仍然未被那一层证明。写法回链 [Java 08](../../java/08-testing/) 与 [微服务 15](../../microservices/15-testing/)，本页不重讲金字塔。

## 全绿没有碰到的性质 {#verification-example}

规格要求并发下总额不变。门禁全绿，列入的检查是单线程的若干输入。这些检查可以证明：在那些输入上，预言没有失败。它们没有并发执行，所以「并发下总额不变」仍未被证明。全绿只证明当时列入的检查已经通过。要把这条性质纳入验证，规格必须写清它（第 03 章），并且采用的手段必须真的碰到并发，或在写明的假设下给出推理。本页不写成流水线配置。

## 常见误读 {#verification-misreadings}

- 「测试通过等于程序正确。」通过只覆盖被执行的输入和正确的预言。Dijkstra 的原话是否定「测试能显示缺陷不存在」，不是说测试不能发现缺陷。
- 「覆盖率到了某一百分比，就接近证明。」覆盖率量的是结构被跑过多少。没跑到的行为和没写进预言的性质都不在这个百分比里。
- 「有 CI 或门禁，验证理论就不需要了。」门禁自动化的是已经选定的检查。它不扩大那些检查的效力，也不代替规格。
- 「形式化方法能证明一切，或完全不能用于工程。」在规格写清且假设成立时，它可以证明特定性质。工作量会随程序变大。这既不是万能，也不是因此作废。

## 可选核对 {#verification-check}

效力表已经列在上面。这两问只核对一次通过建立了哪一条结论。

1. 单线程测试全部通过，覆盖率很高。规格里的「并发下总额不变」被证明了吗？
2. 类型检查通过。能否因此说规格里的每条性质都成立？

<details markdown><summary>参考答案</summary>

1. 没有。这些测试没有并发执行。覆盖率只说明跑过的结构多。该性质不在这次测试的范围内。
2. 不能。类型检查拒绝的是类型规则写明的一类程序。规格里类型不管的性质，这次检查没有建立。
