# 模块与信息隐藏 {#modules-information-hiding}

> [软件工程理论](../) › 模块与信息隐藏

模块把可能独立变化的决策藏在边界后面，使一处修改不必传遍全系统。切分的判据是秘密，不是文件或服务的个数。

## 这一页补哪一块 {#modules-scope}

第 01 章只说变化是前提。本页写分解的判据和成立条件。不写设计模式名录，不画 UML，不重讲微服务怎么拆。[编程](../../programming/) 里的类型与抽象是语言层约定，而且该主题已经不建设计模式目录。本页是工程上「按什么切」的判据。[架构基础与拆分](../../microservices/01-architecture/) 是这一原则的一种实践，不是正文。

## 秘密加上对外的约定 {#modules-secret}

Parnas 的判据是：模块按要隐藏的设计决策来分解，而不是按处理步骤。秘密应当是最可能独立变化的那项决策。对外只留下使用这个秘密的约定。判据选错了，变化就会穿过边界：改一项决策，调用方也得改。

因此模块首先不是一个文件、一个包或一个服务。那些是物理切分。物理上分开，仍然可能把同一项会变的决策露在接口上。反过来，一项秘密也可以由多份源文件实现，只要外部碰不到它。

切得更碎并不自动隐藏得更好。碎片若仍共享同一项秘密，或者接口把表示漏出去，修改次数不会下降，协调成本还会上升。

## 抽象不等于已经隐藏 {#modules-abstraction}

抽象是略去细节以便思考。信息隐藏是禁止外部依赖那些细节。可以有抽象，却没有真正隐藏：接口文档仍然写出内部表示，或者调用方必须知道对方的目录结构才能用。思考时略去了细节，依赖却还在。改表示时，依赖方一起改。

类型上的抽象也一样。语言可以给一个名字，让调用方不写具体表示。[编程](../../programming/) 的类型系统能拒绝一类程序。若接口仍把表示的字段、顺序或存储布局交给调用方，类型名字并没有把秘密藏住。有类型抽象，不等于表示已被隐藏。

## 一起改，说明边界没划对 {#modules-coupling}

耦合说的是模块之间连接有多强，内聚说的是一个模块内部的决定是否属于同一项秘密。这里只用它们当条件，不当打分表，也不列举模式名称。

当两个模块必须一起改，说明秘密划错了，或者接口泄漏了。成立条件有三条：接口稳定，秘密真的只有一处，外部只通过约定使用。反例是把内部表示写进接口文档，或让调用方依赖对方的目录结构。这两种都使「只改秘密」变成「改所有看见秘密的人」。

## 按步骤切，还是按决策切 {#modules-example}

同一件工作可以有两种切法。按处理步骤：先读、再算、再写。按可能变化的决策：存储表示、计算规则、对外格式各藏一处。

只改存储格式时，第一种切法里读和写都看见了格式，两处都要改，算的那一处如果也读了字段，就是第三处。第二种切法里，格式是存储模块的秘密，读和写的调用方只依赖约定。修改落在藏着该决策的那一处。

微服务里的限界上下文是「把一项会变的决定留在边界内」的一种实践。怎么拆服务、怎么画上下文，见 [架构基础与拆分](../../microservices/01-architecture/)。本页不重讲那一课，也不做技术选型。

## 常见误读 {#modules-misreadings}

- 「一个文件或一个服务就是一个模块。」文件和服务是物理边界。模块是一项秘密加上对外约定。物理分开仍可能泄漏决策。
- 「切得越碎，信息隐藏就越好。」碎片若共享秘密或泄漏接口，修改不会更局部，协调会更多。
- 「设计模式名录就是模块化理论。」模式是反复出现的结构名字。本页的判据是「隐藏最可能变化的决策」。名录不是这个判据，本主题也不建模式目录。
- 「有了类型抽象，就一定隐藏了表示。」类型可以给名字。若接口仍暴露表示，外部就仍然依赖它。

## 可选核对 {#modules-check}

判据已经写清。这两问只核对秘密有没有留在边界内。

1. 两个服务各自一个仓库，但接口文档列出了内部记录的字段顺序。改这个顺序时谁要改？
2. 按「先读、再算、再写」切开，只改存储格式。修改会落在几处？

<details markdown><summary>参考答案</summary>

1. 调用方也要改。仓库分开没有隐藏这项决策，因为字段顺序已经写进对外约定。
2. 至少读和写两处；若计算也依赖该格式，就是三处。按步骤切把同一项会变的决策露在了多处。

</details>
