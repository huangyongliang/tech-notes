# 复杂性与变化 {#complexity-change}

> [软件工程理论](../) › 复杂性与变化

软件工程之所以存在，是因为系统要在不完全的理解下被做出来，并且以后一定会被改。工程可以压缩表示上的负担，不能许诺问题本身消失。

## 这一页补哪一块 {#complexity-scope}

本页只划本质复杂性与偶然复杂性，并说明变化是给定条件。不写工期表、团队规模公式，也不开一份「银弹」产品清单。形式限制在 [理论基础](../../cs-theory/)。语言能去掉哪一类错误，在 [编程](../../programming/)。

## 本质的负担和表示的负担 {#complexity-essence}

Brooks 把建造软件的困难分成两类。本质困难来自概念构造本身：它要符合外部世界已经存在的规则，状态与规则会互相制约，而且这个构造会变、又不容易被一眼看见。偶然困难来自把这个构造表示出来时使用的特定语言、工具或过程。

他的结论不是「以后不会再有任何改进」。原文说的是：没有哪一项技术或管理手段，单靠自己就许诺在十年内把生产率、可靠性或简洁性提高一个数量级。高阶语言、分时和统一的编程环境，打的是表示这一侧。它们可以去掉一批偶然困难。问题域里那些互相制约的概念还在。

因此换语言、换框架或换过程，最多压缩偶然复杂性。不能许诺本质复杂性消失。过程正确同样消不掉问题本身的概念负担。过程如果有用，是因为它把变化限制在可管理的范围里，而不是因为它把问题变简单了。

## 变化是前提，不是事故 {#complexity-change-given}

接口、规格和验证之所以需要，是因为后来的修改必须落在当初划定的范围里。本页只提出这个前提。模块如何把「可能变化的决策」藏起来，是第 02 章。哪些性质被写成可检查的约定，是第 03 章。一种检查究竟证明了什么，是第 04 章。

「一次把需求写完，以后就不必再谈变化」把变化当成可以结束的事故。Brooks 把可变性列在本质困难里：软件被嵌入的世界在变，成功的软件还会被要求做最初没写到的事。写完一份说明，并没有取消后来的修改。

## 不要换成另外两种「复杂」 {#complexity-not-theory}

不可判定，或复杂度上的上界，说的是一类问题的形式限制。那是 [理论基础](../../cs-theory/) 的对象。本页的「复杂」是概念与变化上的负担。不能从「这个问题在工程上难」推出「所以它不可判定」，也不能从一条不可判定结论推出「所以任何工程约束都没用」。

换一种语言或类型系统，可能去掉一类偶然错误，例如把一种非法使用挡在翻译期。[编程](../../programming/) 写的是语言约定能保证什么。它不自动减少问题域里必须同时满足的那些规则。类型系统拒绝的是它写明要拒绝的程序，不是业务规则之间的相互制约。

## 同一条规则，两种表示 {#complexity-example}

规则是「订单不可超卖」：卖出的数量不能使剩余变成负数，并且每次拒绝或接受都要留下可核对的结果。这是问题本身的相互制约。无论用什么表示，这条规则都还在。

表示可以不同。一种是集中在一处校验剩余。另一种是把同一判断分散写进多处脚本。后一种增加的是偶然复杂性：改规则时要找到每一处，漏一处就和规则不一致。前一种把表示上的重复拿掉了。两种表示都没有让「不能超卖」这条规则消失，也没有设计一套库存系统。本页停在这个对照。

## 常见误读 {#complexity-misreadings}

- 「换新语言或新框架，复杂性就会消失。」它们至多去掉表示和工具带来的偶然困难。概念之间的制约还在。
- 「只要过程正确，本质复杂性也能被过程消掉。」过程可以限制变化落在哪里。它不把问题域变小。
- 「工程上的困难就是不可计算。」形式限制和概念负担不是同一句话。前者回链理论基础，后者是本页的对象。
- 「一次把需求写完，以后就不必再谈变化。」变化是本质困难的一部分。写完说明并没有取消后来的修改。

## 可选核对 {#complexity-check}

分界已经写在上面。这两问只核对一种手段打在哪一侧。

1. 把分散的超卖判断收成一处校验。消失的是本质复杂性还是偶然复杂性？
2. 一条业务规则很难一次想全。这是否说明该问题不可判定？

<details markdown><summary>参考答案</summary>

1. 偶然复杂性。规则「不可超卖」仍在。收成一处只是让修改不必穿过多份脚本。
2. 不能。难想全是概念与变化上的负担。不可判定是理论基础里的形式限制，本页不把二者写成同义词。

</details>
