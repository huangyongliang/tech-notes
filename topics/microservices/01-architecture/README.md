# 架构基础与拆分 {#architecture-decomposition}

> [微服务](../) › 架构基础与拆分

从单体到微服务的动因与代价，用 DDD 的限界上下文划分服务边界。涵盖绞杀者模式、模块化单体（Spring Modulith）和康威定律。

理论部分参见 [系统](../../systems/)（CAP、一致性、共识）。

## 本关定位

拆分是微服务体系的第一步：边界划错，后面网关、事务、可观测再完善也救不回来。本关建立「何时拆、按什么拆、怎么渐进拆」的判断力，不急着上全套中间件。

## 知识要点

### 何时拆、何时不拆

适合拆：多团队并行交付、不同扩展维度、明确的故障隔离需求。不适合拆：领域边界尚未稳定、运维与可观测能力不足、团队规模过小却强行「一人一服务」。

### 限界上下文与服务边界

一个限界上下文通常对应一个可独立演进的服务（或模块）。以「请假审批」为例：假期额度、审批流、考勤统计可以是不同上下文，通过领域事件协作，而不是共享一张大表。

```mermaid
flowchart LR
  A[单体应用] --> B[识别限界上下文]
  B --> C[模块化单体]
  C --> D[按上下文拆服务]
  D --> E[绞杀者渐进替换]
```

### 模块化单体与 Spring Modulith

在彻底拆进程前，先用包结构与模块边界强制依赖规则。Spring Modulith 2.1.2 可做模块验证、事件发布与文档生成，降低「拆完发现还是分布式单体」的风险。下面的监听方法补上 `@` 后，已在 2026-11-06 用 JDK 21.0.12.1 对 `spring-modulith-events-api` 2.1.2 与 Spring Framework 7.0.10 编译通过。`LeaveApprovedEvent` 和 `attendanceService` 是示意类型，不是完整应用，未运行。

```java
@ApplicationModuleListener
void onLeaveApproved(LeaveApprovedEvent event) {
    attendanceService.recalc(event.employeeId());
}
```

### 绞杀者模式

新功能进新服务或新模块；旧路径逐步把流量切到新实现；最后拆除遗留代码。关键是用门面 / 路由层控制切换，并保证读写路径的数据一致性策略事先想清楚。

## 选型对比

| 形态 | 适用 | 优点 | 代价 |
|------|------|------|------|
| 单体 | 小团队、边界未定 | 简单、事务容易 | 扩展与发布耦合 |
| 模块化单体 | 准备拆分、仍单进程 | 边界清晰、部署简单 | 仍共享运行时 |
| 微服务 | 多团队、独立扩展 | 自治、技术异构 | 分布式复杂性高 |

## 常见误区

- 按技术层拆（「用户 Controller / 用户 Service」各成服务），而不是按业务能力。
- 一上来就上服务网格、全链路追踪，却没有稳定的领域边界。
- 共享数据库却自称微服务——本质仍是分布式单体。
- 忽视康威定律：组织结构不支持独立交付时，硬拆只会增加协调成本。

    - C. 替代 Kubernetes
    - D. 替代 API 网关
3. 【简答】为什么「共享一个数据库的多个服务」通常不算合格的微服务？
4. 【单选】限界上下文划分服务边界时，更合理的依据是：
    - A. 代码行数是否超过 1000
    - B. 业务语言与模型是否一致、能否独立演进
    - C. 是否使用同一编程语言
    - D. 是否部署在同一机房
5. 【简答】康威定律对微服务拆分有什么启示？

<details markdown><summary>参考答案</summary>

1. B — 新旧并存，经门面 / 路由渐进替换。
2. B — 在单体（或尚未拆进程）阶段强制模块边界。
3. 服务仍通过同一库强耦合 schema 与事务，无法独立演进与扩展，是分布式单体。
4. B — 以统一语言与可独立演进的模型为准。
5. 组织沟通结构会映射到系统结构；拆服务需匹配团队边界与交付方式，否则协调成本更高。
